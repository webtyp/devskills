# Project Layout — the one directory distribution

Every application built on the tinywasm framework (`veltylabs/*`,
`mjosefa-cms`, `iam`, `misitio`, …) uses **this** directory distribution — not
another. The only things that vary between projects are two **additive**
directories:

- **`edge/main.go`** — added for a cloud project deployed as a Cloudflare
  Worker via `tinywasm/goflare`.
- **`cmd/migrate/main.go`** — added when the schema is reconciled from CI/CD
  or run manually (never inside the Worker's `main()` — that costs seconds of
  cold start).

Everything else below is fixed.

```text
/
├── config/                  // NÚCLEO: the single composition root (merges app/ + client/)
│   ├── config.go            // neutral: AppName, DefaultModuleID, Modules() — shared symbols
│   ├── server.go            // (!wasm)  ServerConfig, ServerDeps, BuildServer(), RunServer()
│   ├── client.go            // neutral: ClientConfig, ClientDeps, BuildClient() → *platformd.Platform
│   ├── css.go               // (!wasm)  RootCSS() global theme — MUST be an importable package (ssr imports it)
│   ├── lang.go              // neutral: init() registers the app's lang.RegisterWords dictionary + lang.OutLang(...)
│   └── layouts/             // leaf package for design presets (avoids import cycles)
│       └── crud.go          // neutral: the app's standard preset over crudview
├── modules/
│   ├── init.go              // neutral: Init(db, caller, ids, pub) []any — single registry, one append per module
│   └── <module_name>/
│       ├── init.go          // neutral: Init(db, caller, ids, pub) []any — backend (if db) + view (if caller)
│       ├── backend.go       // (!wasm) newBackend(...) — returns the domain library's *Module
│       ├── model.go         // neutral: model.Definition literals (only if this module owns tables)
│       ├── model_orm.go     // GENERATED by ormc — never hand-edit
│       ├── svg.go           // (!wasm) Icon = sprite.Define(...) — per-module CSS/icons
│       └── view.go          // neutral: the module's VIEW, built via <domainlib>.NewView(caller)
├── tests/                   // EVERY test in the repo lives here — package tests, imports config
│   ├── setup_test.go            // TestMain, buildUnderTest(), generic fakes
│   ├── <m>_contract_test.go     // real caller ↔ httptest
│   ├── <m>_view_mock_test.go    // mock caller for the view
│   ├── <m>_view_test.go         // view: neutral (no tag)
│   └── <m>_view_wasm_test.go    // view: //go:build wasm — real DOM, activates the browser suite
├── web/                     // ONLY thin main() — no logic, no theme, no wiring
│   ├── client.go            // (wasm)  main(): origin → config.BuildClient
│   ├── server.go            // (!wasm) main(): env    → config.RunServer
│   └── public/              // static assets (index.html, generated CSS, wasm, JS runtime)
│
├── edge/main.go             // (wasm, OPTIONAL) Cloudflare Worker entrypoint — goflare projects only
└── cmd/migrate/main.go      // (!wasm, OPTIONAL) schema reconciliation for CI/CD or manual runs
```

## The invariants

### 1. `config/` is the composition root — one package, not `app/` + `client/`

Server and client share real symbols (`AppName`, `DefaultModuleID`, the
module list, security-event names). Two packages can't share them without
inventing a third. `config/` defines them **once** in a neutral file; both
targets see it. Each file is a **configuration layer**:

- `config.go` — neutral (no build tag): shared constants + `Modules()`.
- `server.go` — `//go:build !wasm`: `ServerConfig`, `ServerDeps`,
  `BuildServer() (*httpd.Server, error)` (pure, doesn't listen — testable
  with `httptest`), `RunServer()` = Build + ListenAndServe.
- `client.go` — **neutral** (so the view rail runs in stdlib tests):
  `ClientConfig`, `ClientDeps`, `BuildClient() → *platformd.Platform`.
- `css.go` — `//go:build !wasm`: `RootCSS()` global theme.

**Naming rule — never `config.Config`.** `client.go` is neutral and
`server.go` is `!wasm`, so under `!wasm` compilation both compile at once. A
`config.Config` defined in both would collide. Types are explicit per layer:
`ServerConfig`/`ServerDeps`/`BuildServer` vs `ClientConfig`/`ClientDeps`/
`BuildClient`. Zero-value deps = production wiring; injected doubles = test.

### 2. Dependency direction: `config → modules`, NEVER `modules → config`

The core depends on the leaves, never the reverse. `config/` must not be
imported by anything under `modules/`. A module that needs a shared preset
imports `config/layouts/` (a leaf that imports neither `modules` nor
`config`). Verify: `grep -rn "<module-path>/config" modules/` → empty.

### 3. `web/` is thin `main()` only

`web/server.go` / `web/client.go` are `package main` — **not importable from
`tests/`**. They only resolve config from the environment/origin and call
`config.RunServer` / `config.BuildClient`. No logic, no theme, no wiring
lives here. (This is why `RootCSS()` is in `config/css.go`, not `web/`: the
`ssr` extractor *imports* the package exposing `RootCSS()`, and a `package
main` is not importable.)

### 4. A module is a capability bag; its VIEW lives in `view.go`

Each `modules/<m>/init.go` exposes `Init(db, caller, ids, pub) []any` — a bag
of typed capabilities: a **backend** (`mcp.ToolProvider` / `router.OpModule`)
when `db != nil` (server), a **view** (`platformd.UIModule`) when `caller != nil`
(browser). `modules/init.go` appends every module's bag. Consumers dispatch by
type in silence — an item that isn't their type belongs to the other target;
`nil` is ignored.

- The **view** is built in `view.go` via `<domainlib>.NewView(caller)` and
  wrapped in a `platformd.UIModule`. **All of a module's view construction
  goes in `view.go`** — never scattered across other files. Domain-specific
  interactive wiring may live in area-named files, but the view itself is
  `view.go`.
- `backend.go` (`!wasm`) returns the domain library's `*Module` — `nil` in,
  `nil` out; never constructs an id generator inside.
- Per-module CSS/icons live in that module's dir (`svg.go`, `css.go`), read by
  `ssr` only from files named exactly `css.go`/`js.go`/`svg.go`/`html.go`.
- **Flat: no subdirectories inside a module.** `find modules -mindepth 2 -type d` → empty.
- Canonical file names: `init.go`, `backend.go`, `model.go`, `model_orm.go`
  (generated), `view.go`, `svg.go`, `css.go`. Same set as
  `mjosefa-cms/modules/<m>/` and `veltylabs/modules/item_catalog/`.

### 5. Every test in `tests/`

TODO test of the repo — unit, view, WASM view, contract, integration — lives
under the root `tests/` directory (`package tests`, imports `config`). Nothing
in `modules/` or `config/` carries a `_test.go` file. Run with `gotest` (never
`go test`): it runs native + browser in one command; the wasm suite activates
by `//go:build wasm`, not by name.

### 6. Neutral vs `!wasm` files

Neutral files (no build tag) import only cross-platform types — they compile
in stdlib tests *and* wasm. `!wasm` files (`svg.go`, `css.go`, `server.go`)
may import SSR types. A neutral file that imports an SSR-only package breaks
the view test rail.

### 7. `config/lang.go` is the app's one translation dictionary

A tinywasm library never hardcodes a human language for its own chrome text
(dialog titles, confirmation messages, calendar month/weekday names, …) —
it renders the English canonical word through `lang.Translate(...)`
(`github.com/tinywasm/fmt/lang`) and registers nothing itself. `config/lang.go`
is where the APP decides: an `init()` calling `lang.RegisterWords([]lang.DictEntry{...})`
for every word a library it uses actually renders, plus `lang.OutLang(...)`
to activate the target language. Neutral (no build tag) — translated text
can render on either the server or the client side. It has no effect unless
something imports `config` (an `init()` in an unimported package never
runs) — `web/client.go` (and `web/server.go`, if present) must import
`config`, even if only blank (`_`), same as any other composition-root
side-effect import. Adding a module that pulls in a new component with its
own translatable chrome adds words to this SAME file — never a second
dictionary file. Full rationale and the consumer-side contract:
`https://github.com/tinywasm/layout/blob/main/docs/DICTIONARY.md`.

## Transport variants

The canonical transport is **MCP** (`mcp.HarvestOps` on the server,
`mcp.NewCaller(mcp.NewClient(origin, ""))` on the client). HTTP/REST stays for
binary uploads, static SSR, and auth flows.

A project may instead use **plain REST** for its own API (e.g. a Cloudflare
Worker where MCP-over-goflare is unproven). Then:

- A `routes/` folder appears with **`routes/routes.go` as a single mount
  table** — every `r.Get/r.Post/...` with its `.Public()`/`.Authenticated()`,
  and nothing else. It is the REST equivalent of `modules/init.go`'s
  op-registration.
- The renderer-touching half of the modules moves to a `modules/panel/`
  package (`//go:build wasm`) that `routes/` **never** imports — that missing
  import is the package boundary keeping `dom`/`layout`/`crudview` out of
  `edge.wasm` (a build tag is not enough: `goflare`/`sitec` pass no `-tags`).
- Server-side handler modules stay flat under `modules/<domain>/`
  (`handler.go`, `backend.go`).

Everything else — `config/` as leaf composition root, thin `web/` mains, all
tests in `tests/`, views in `view.go`, no subdirs in a module — is unchanged.

## When adding the optional dirs

- **`edge/main.go`** (`//go:build wasm`): builds the D1/R2 bindings, calls
  `config.New...`/`routes.Register` (or the MCP mount), `edge.Serve(r)`. It
  never does schema DDL.
- **`cmd/migrate/main.go`** (`//go:build !wasm`): reads `CLOUDFLARE_*` /
  `D1_*` env, runs each package's `Migrate`/`Sync` against the D1 HTTP API.
  Invoked from the deploy workflow (`pre-deploy: go run ./cmd/migrate`) or by
  hand. Thin main: parsing + DI + print/exit only.

## Checklist for a structure review

- [ ] `config/` imports nothing from the repo's own module tree.
- [ ] `web/*.go` are `package main`, contain only env/origin resolution + a call into `config`.
- [ ] `RootCSS()` is in `config/css.go` (`!wasm`), not `web/`.
- [ ] `config/lang.go` holds the app's only `lang.RegisterWords` call; no library registers its own dictionary; `web/client.go` (and `web/server.go`) import `config`.
- [ ] Every `modules/<m>/` has flat files only; its view is in `view.go`.
- [ ] No `_test.go` outside `tests/`.
- [ ] `config.Config` does not exist — types are `ServerConfig`/`ClientConfig`.
- [ ] `edge/main.go` does no schema DDL; `cmd/migrate/main.go` is a thin main.
- [ ] (REST projects) `routes/routes.go` is the only file with `r.Get/r.Post`; `routes/` never imports `modules/panel/`.
