# Project layout

A new directory or file convention is public API: **api-design** first.
Module files: **app-modules**. Generated server main: **app-server-main**. REST / Cloudflare variant: **app-rest-edge**.

```text
/
├── config/            // the single composition root: it only configures
│   ├── app.go         // no tag: var App = appkit.App{TenantID, Timezone, Brand, Modules, Server, Log}
│   ├── server.go      // !browser: var server = appkit.AppServer{Database, MCPTools, Routes}
│   ├── browser.go     // browser: var server appkit.AppServer (the wasm links no server)
│   ├── brand.go       // no tag: var Brand = appkit.Brand{Name, LogoMark}; sitec renders the access page from it
│   ├── mcp.go         // !browser: MCPTools() — operations an agent may call
│   ├── css.go         // !wasm: RootCSS() global theme (read by sitec)
│   ├── favicon.go     // !wasm: Favicon() favicon.Source (generated by webtyp, with its dependency)
│   ├── deploy.go      // deploy: deploy.Plan, read by AST, linked by no binary
│   ├── lang.json      // the app dictionary (skill langc)
│   └── migrations.go  // !wasm: GENERATED: var Migrations = []ddl.Step{...} in App.Modules order (read by migrate & devtools)
├── migrate/main.go    // GENERATED: migrate.App(config.App.Server.Database, log.Println, config.Migrations...) (runs with go run ./migrate)
├── tests/             // EVERY test of the repo
├── web/               // the only output folder: no .build/, no edge/ at the root
│   ├── browser/main.go // GENERATED: appkit.Browser(config.App, devtools.Menu()) → web/public/browser.wasm
│   ├── server/main.go  // GENERATED (skill app-server-main): appkit.Server(config.App, devtools.Server(config.Migrations...)...) → web/server/server
│   ├── edge/main.go    // optional Worker → web/edge/edge.wasm + web/edge/edge.js
│   └── public/         // the only thing served, to anyone: never a binary
```

Each module is named once in `App.Modules` (its `module.Module`, skill **module-layout**): appkit builds the server
part and draws the menu from its screens (entry is `webtyp.com/access/module`). No `config/auth.go`,
`config/html.go`, `config/routes.go`, `modules/` registry or hand-written migrate command. A tagless file references
only what exists under every tag: what belongs to one binary goes in a tagged file and its pair. Server-only
migrations list lives in `config/migrations.go` (`!wasm`).

STATUS (remove this line when MVP_DEPLOYMENT_ROADMAP closes): an app never commits a `compose.yaml` or `Dockerfile`; for a self-hosted server the target `selfupdate.Server` of `webtyp/selfupdate` generates the compose on the server from `config/deploy.go`. The entry point folder under `web/` determines the deployment target: `web/edge/` → Worker (`goflare.Worker`, `github.Actions`); `web/server/` only → Server (`selfupdate.Server`, `gorelease.Local`).


**`appkit` is production only.** It is the piece an app ships: isomorphic (same declaration for server and browser)
and agnostic of development. Development operations (running migrations on save, diagrams, introspection, demo
tools) live in the piece responsible for them and are driven by `webtyp/app` (`webtyp dev`), never added to `appkit`.

## Build tags: two axes, one name per binary

The **folder** under `web/` says which binary a main builds; a main carries no destination tag (at most `wasm`/`!wasm`), because a tag of our own (`browser`) hides the file from gopls. Relative paths (`web/public`) resolve against the process's working directory, never the binary's folder: every launcher starts it at the project (or package) root. **Platform** `wasm`/`!wasm` is set by the compiler (`GOARCH=wasm`, browser **and** Worker). **Destination** `browser`/`!browser` is passed only by the client compiler (`-tags browser`, `browser,dev` in development); `goflare` refuses it and the native server passes none.

| Runs in | Tag |
|---|---|
| browser only | `browser` |
| Worker only | `wasm && !browser` (rare: the Worker main needs none, its folder separates it) |
| native server only | `!wasm` |
| browser + Worker | `wasm` |
| native server + Worker | `!browser` |
| all three | none |

**No other tag.** App and library code uses only `wasm`/`!wasm`, `browser`/`!browser` and `dev`/`!dev` (development only: `DEV_AUTOLOGIN`; the normal build **is** production). Never invent one (`prod`, `server`, `local`): a file behind a tag nobody passes is never compiled and breaks unseen (mjosefa-cms, 2026-10-28). Code that talks to the operating system keeps Go's own `windows`/`linux`/`darwin`; opt-in test suites keep theirs.

Rule: *why is it split?* The API does not exist on that platform (`syscall/js`, `os`, `net`) → `wasm`/`!wasm`. It belongs to another binary → `browser`/`!browser`. Libraries carry no destination tag — the linker already drops what a binary never calls, so server-only code of a library (an SVG generator, an endpoint) stays untagged — and keep `wasm`/`!wasm` only for a missing API; only a library file imported by both browser and Worker that must behave differently uses `browser`. Every destination is tested on its platform (`gotest` runs one pass per destination: skill **testing**).

## Invariants

1. **`config/` is one package** and declares one value, `config.App`, read by every binary — **never `config.Config`**. Tests edit a copy (`app := config.App; app.Server.Database = …`).
2. **`config → modules`, never `modules → config`**: a module never imports the app.
3. **`web/<binary>/` is `package main` only**: env/origin resolution + a call into `config`. `RootCSS()` lives in `config/css.go` because `sitec` imports it and a `main` is not importable.
4. **Every test in `tests/`** (`package tests`, imports `config`); run with `gotest` (skill **testing**).
5. **An untagged file compiles into all three binaries**: it imports only cross-platform packages. Server logic is `!browser`, renderer code is `browser`, asset producers are `!wasm`. Consequence for any tool that computes a build graph: the asset files of a browser-only package, and what they import, exist only in the **native** graph **with** `-tags=browser` — probe each platform with and without the destination tag, never one combination per platform.
6. **The app chooses the database, and only the app.** The concrete engine (`postgres`, `sqlite`, `indexdb`, `storage/mem`) is imported only in `config/`, `web/*/main.go`, `cmd/` or tests. Every library — `appkit`, `dbsync`, `changelog`, `orm`, the modules — receives the connection through the engine-agnostic contracts (`storage`, `orm`) and never opens or picks one; depending on those contracts is fine, they run in server, Worker and browser alike. Check: `grep -rln 'webtyp.com/postgres\|webtyp.com/sqlite\|webtyp.com/indexdb' --include=*.go <library> \| grep -v '_test.go\|/tests/'` → empty.

## Review checklist

- [ ] `config/` imports nothing from the repo's module tree.
- [ ] `web/<binary>/main.go` only resolves config and calls `config`; no destination tag.
- [ ] Own routes, if any → `AppServer.Routes` (one-parameter, **app-server-main**); no empty `config/routes.go`.
- [ ] `RootCSS()` in `config/css.go`.
- [ ] Module checklist of **app-modules** passes.
- [ ] No `_test.go` outside `tests/`; no `config.Config`; no `edge/`, no `.build/`.
- [ ] `.gitignore`: `/web/public/`, `/web/server/server`, `/web/edge/edge.*`.
